## §4 — DÉCISIONS À TRANCHER (une recommandation ferme par point)

1. **Four-eyes sur ban/purge définitifs** → **2 phases avec intention enregistrée** : l'admin A crée `PendingDestructiveAction {action, targetId, reason, requestedBy=A}` (statut `pending`) ; l'admin B (session **distincte**, rôle ≥ moderator, B ≠ A) voit la file des intentions et clique « Approuver » → exécution + `AdminAudit{requestedBy:A, approvedBy:B}`. Pas de token externe, pas d'email ; rejet possible ; auto-expiry 48 h (job au boot). C'est le mécanisme le plus simple qui donne : double consentement, traçabilité nominative, refus auditable.
2. **Break-glass (perte 2FA)** → **2 codes de secours hachés à l'enrollment** (Argon2id, usage one-time : le code consommé est marqué + entrée `AdminAudit` + les autres super-admins voient un bandeau à la prochaine connexion). La procédure « documentée mais non automatisée » seule est **insuffisante** (un super-admin bloqué sans l'app = immobilisation de la modération). Test obligatoire du flux à l'enrollment (1 code consommé en démo puis régénéré).
3. **Rétention `AdminAudit`** → **Illimité (jamais purgé)**. Volume = actions admin seulement (pas de contenu utilisateur) — croissance négligeable à l'échelle MVP ; toute purge de traces est par nature un risque supérieur à son coût ; append-only + rétention illimitée = promesse cohérente au régulateur. Réévaluer à > 1 M lignes (export/archive alors, jamais delete).
4. **Justification d'investigation (email/IP)** → **renforcer** : champ texte **min 20 caractères** (au-delà du « obligatoire »), + **motif catégoriel** fermé (dropdown : signalement / litige / sécurité / légal), stockés dans `AdminAudit` (lignes visibles dans le viewer, non modifiables). Un champ texte libre court est trop faible pour dissuader la curiosité ; la paire catégorie+20c est contraignante sans être dissuasive à l'usage.
5. **Cloudflare Access vs IP allowlist** → **CF Access requis** (la zone est déjà sur CF — §1.4 ; Access est disponible sur les plans gratuits dans la limite des users). Vérification = **action opérateur** (dashboard CF → Zero Trust → Access → app sur `admin.aenews.online`, politique email OTP des 2–3 admins). **Fallback acceptable si CF Access indisponible : IP allowlist nginx** (l'outil `nginx-cf-lockdown.sh` prouve la maîtrise de la mécanique) + 2FA obligatoire + TTL sessions courts. **Refuser le déploiement du panneau sans AU MOINS UN des deux** — c'est la frontière entre panneau interne et surface d'attaque publique.

## §5 — SÉQUENCEMENT

**B1 vs ADM : « non mais »** — aucun des deux n'a de dépendance code sur l'autre **aujourd'hui** (B1 n'existe pas : §0.2 ; l'admin n'existe pas non plus). « Non, ils ne se bloquent pas » — « mais » l'ordre a une conséquence produit : **B1 livrera du média signalable** → sans panneau, la modération du média se fera par API/CLI (supportable : la queue A3 + `moderation-purge.ts` couvrent hide/purge/suspend). 

**Recommandation : ADM d'abord, B1 ensuite** — justifications ancrées : (1) A3 a documenté lui-même la dette : « auth admin PROVISOIRE… à remplacer par un RBAC complet AVANT ouverture publique » (`moderation.ts:11–13`, `A3-moderation.md`) — chaque semaine de média sans panneau creuse cette dette ; (2) le média augmente le volume de signalements (surface modération) — l'UI queue est plus utile avant qu'après ; (3) aucun coût de rebase dans l'ordre ADM→B1 (branches vierges des deux côtés) ; (4) si B1 démarre avant, la seule chose qui « casse » est organisationnelle (modération média au CLI pendant l'attente) — rien de technique.
Si l'opérateur privilégie la roadmap initiale (B1 recommandé à la clôture des incidents), **B1 → ADM reste défendable** : A3 couvre le minimum vital.
